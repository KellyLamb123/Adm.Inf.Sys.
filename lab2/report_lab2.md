

<h1>Часть 1. Создание сервиса</h1>

В первой части мы сделали небольшой тестовый сервис на Python с помощью Flask. Сам сервис максимально простой и подробного объяснения, думаем, не стоит. Основной функционал - три кнопки на главной странице: Cause an error, Cause a delay, Load. 

Первая кнопка отправляет запрос, который заканчивается ошибкой сервера с кодом HTTP 500. При этом счётчик ошибок увеличиватся и в логи записывается инфа о том, что произошла ошибка. Это необходимо для дальнейшего мониторинга сервиса различными инструментами, о которых речь пойдет дальше

Вторая кнопка работает немного по-другому. Запрос не падает и в итоге возвращает обычный HTTP 200, но перед ответом сервис специально ждет примерно от 1 до 3 секунд. Таким образом, мы имитируем ситуацию, когда сервис работает нормально, но начинает долго отвечать.

Кнопка Load нужна уже для имитации нагрузки. При нажатии сервис сам отправляет несколько десятков запросов на свой /work endpoint. За счет этого за короткое время резко увеличивается количество запросов и дальше на графике можно будет увидеть скачок RPS.

Еще мы сделали endpoint /metrics. В нем сервис отдает метрики в Prometheus. Основные метрики у нас это общее количество запросов, количество ошибок и время выполнения запросов. Для времени используется histogram, чтобы потом можно было считать не только среднее время ответа, но например и p95.

Также сервис пишет структурированные логи в JSON. Например, при ошибке логи содержат уровень события, сообщение и trace_id. JSON здесь удобен тем, что это отдельные поля, а не одна строка текста, по которым потом можно искать и фильтровать логи.

OpenTelemetry мы тоже сразу добавили в приложение, хотя непосредственно Jaeger будет подключаться уже в другой части работы. Для каждого HTTP-запроса создается trace, а для медленного запроса дополнительно сделан отдельный span slow-dependency. Для ошибки span помечается как ошибочный. Еще trace_id этого же запроса записывается в логи, чтобы потом можно было связать конкретный лог с конкретным trace.

Сам сервис мы завернули в Docker. Для этого сделали Dockerfile, где используется Python 3.12, устанавливаются библиотеки из requirements.txt, а также копируется наш код и запускается app.py. За счет этого не нужно отдельно устанавливать все зависимости на компьютер, так как они находятся внутри контейнера.

После сборки контейнера мы отдельно проверили все три кнопки и /metrics. При нажатии Error счетчик ошибок действительно увеличиваетсяся, Delay даёт задержку перед ответом, а после Load сильно увеличиваетсяь количество запросов.

Таким образом, в первой части ЛР мы подготовили почву для дальнейшего мониторинга и анализа проиходящих на нашем сайте событий.

Часть 2. Создание сервиса

Во второй части мы подключили к сервису Prometheus. Для него сделали отдельный файл - prometheus.yml, где указали, что метрики нужно собирать каждые 5 секунд. 

Для запуска уже нескольких контейнеров мы сделали docker-compose.yml. Сначала через него запускались наш сервис и Prometheus, позже туда же добавили Grafana. Это намного удобнее, чем вручную отдельно запускать каждый контейнер через docker run.

После запуска мы открыли страницу Targets в Prometheus и проверили, что наш сервис имеет статус UP. Это значит что всё гуд и инструмент работает.

Потом через интерфейс Prometheus проверили сами метрики. После семи нажатий на Cause an error значение http_errors_total стало равно семи. После Load заметно вырос http_requests_total. 

После этого подключили Grafana. Для RED dashboard используются три основных показателя: Rate, Errors и Duration.

Для Rate мы смотрим скорость роста счетчика запросов (сколько запросов примерно приходит в секунду). При нажатии Load это значение ио идее должно резко подниматься.

Для Errors считается доля запросов с HTTP-кодами 5xx относительно общего количества запросов. Если мы несколько раз нажимаем Cause an error, процент ошибок должен на графике увеличиваться.

Небольшой нюанс с метриками, который мы заметили в процессе:

Prometheus сам каждые 5 секунд обращается к /metrics, и наш сервис считает этот запрос точно так же, как остальные HTTP-запросы. Поэтому даже когда мы сами вообще ничего не нажимаем, счетчик запросов постепенно увеличивается. 

В идеале можно было бы исключить endpoint /metrics из запросов для RPS и некоторых расчетов. Например считать только endpoint != "/metrics". 

Но сами данные мы решили специально оставить максимально близко к тому, как сервис реально работает. Благодаря этому видно, что Prometheus действительно постоянно общается с приложением. А для лабораторной это даже наглядно показывает, что мониторинг взаимодействует с сервисом по-настоящему.

Еще один момент был с rate. Этот запрос смотрит именно на изменение метрики за последнюю минуту, поэтому если долго не создавать новых ошибок, то Grafana может ничего и не показать или значение по-просту вернется к нулю. То есть прошлые семь ошибок из счетчика никуда не пропадут, просто для текущего error rate будут важны новые события за выбранный промежуток времени.

Что мы имеем по итогу?

-Сервис генерирует данные
- Prometheus регулярно их собирает и хранит
- Grafana уже берет данные из Prometheus и позволяет показывать их в нормальном виде на графиках. 

Самое главное, что три кнопки дают возможность вручную менять разные показатели системы. Load влияет в основном на Rate, Error на Errors, а Delay на Duration.
